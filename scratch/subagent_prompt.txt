STEP 25A — MEMBER UAT & UX WALKTHROUGH
=======================================

OBJECTIVE
---------

Audit the BBS Member experience as if the application is being used by a
real BBS member who has NO knowledge of the database, RPCs, internal
status machine, or implementation details.

This is a PRODUCT / UX audit.

Do NOT redesign the application from scratch.
Do NOT change business rules.
Do NOT modify database/RPC logic unless a UI issue exposes a real
domain integration defect.

First AUDIT.
Then REPORT.
Only implement fixes after the audit identifies concrete problems.

==================================================
B. FIRST IMPRESSION
==================================================

Audit:

- Is it immediately clear that this is the BBS Member app?
- Is the current state understandable?
- Is the primary action obvious?
- Is navigation understandable?
- Is there unnecessary information?
- Are important actions visually prioritized?
- Is the terminology understandable to a normal member?

Do not judge based only on design taste.

Focus on usability and task completion.


==================================================
C. MEMBER HOME
==================================================

Audit the current Home screen.

Check:

- membership status
- remaining credits
- upcoming booking
- pending booking
- expired membership
- no membership
- zero credits
- notifications
- primary CTA

For each state determine:

1. What does the user see?
2. What can they do?
3. Is the next action obvious?
4. Is any information contradictory?


==================================================
D. SCHEDULE
==================================================

Audit:

- date navigation
- available slots
- full slots
- closed slots
- past slots
- membership priority if applicable
- booking CTA
- loading state
- empty state
- error state

Check that the UI never suggests an action that the backend will
immediately reject for a normal, foreseeable reason.

Do not duplicate backend business rules unnecessarily in the UI,
but identify places where basic UX prevention is appropriate.


==================================================
E. BOOKING CREATION
==================================================

Walk through creating a booking.

Audit:

- participant selection
- participant count
- membership selection
- credit visibility
- confirmation step
- loading state
- success state
- error state
- duplicate click protection

After successful creation verify the user clearly understands:

    "My booking is pending."

The UI should not imply that the session is already confirmed.


==================================================
F. BOOKING DETAIL
==================================================

Audit every important booking state:

    PENDING
    CONFIRMED
    RESCHEDULE_REQUESTED
    REJECTED
    MEMBER_CANCELLED
    BBS_CANCELLED
    COMPLETED
    NO_SHOW
    EXPIRED

For each state:

- status label
- explanation
- available actions
- unavailable actions
- cancellation/reschedule semantics
- relevant date/time
- participant information
- credit implication where appropriate

Do not expose internal technical terms such as:

    RPC
    ledger
    aggregate_id
    domain error

unless intentionally designed for the user.


==================================================
G. RESCHEDULE UX
==================================================

Audit:

    CONFIRMED
      ↓
    Reschedule
      ↓
    Select new slot
      ↓
    Request submitted
      ↓
    RESCHEDULE_REQUESTED
      ↓
    Admin approve/reject

Verify the user understands:

- current slot
- requested slot
- that reschedule is pending approval
- what happens if rejected
- whether credit changes
- when reschedule is no longer available

Pay special attention to the newly fixed H-6 restriction.

If the UI currently allows the user to click Reschedule inside the
deadline window, determine whether the UX should proactively disable it
or explain why it cannot proceed.

Do not invent a new business rule.


==================================================
H. CANCELLATION UX
==================================================

Audit:

    early cancellation
    late cancellation
    BBS cancellation

The user must be able to understand the consequence BEFORE confirming.

Check whether the UI clearly communicates:

- cancellation timing
- credit consequence
- whether the credit is returned
- whether the booking becomes cancelled

Do not expose internal ledger transaction names.


==================================================
I. NOTIFICATIONS
==================================================

Audit the Member notification experience.

Check:

- booking confirmation
- rejection
- BBS cancellation
- reschedule-related notifications if supported
- read/unread state
- empty notification state
- navigation from notification to relevant booking
- stale notification state

Do not claim actual FCM device delivery verification.


==================================================
J. LOADING / EMPTY / ERROR STATES
==================================================

Explicitly inspect every major Member page for:

    Loading
    Empty
    Error
    Success
    Disabled
    Pending

Do not accept:

- blank screen
- infinite spinner
- raw Supabase error
- raw Postgres error
- undefined
- null
- technical enum values shown to users


==================================================
K. AUTHORIZATION / ACCOUNT BOUNDARY
==================================================

Verify a Member cannot access another Member's:

- booking
- membership
- profile
- notification
- credit state

Check actual route guards/server authorization.

Do not test by modifying production data.


==================================================
L. MOBILE / PWA
==================================================

Test the Member journey at mobile dimensions.

Audit:

- bottom navigation
- sticky CTA
- modal height
- scrolling
- keyboard interaction
- safe areas
- touch targets
- overflow
- text truncation
- date/time readability
- back navigation

Focus on practical usability rather than aesthetic preference.


==================================================
M. UX CONSISTENCY
==================================================

Check terminology consistency.

Examples:

    Booking
    Session
    Ride
    Reschedule
    Cancel
    Confirmed
    Pending
    Completed

The same concept should not have multiple unexplained labels.

Also check:

- button styles
- status pills
- modal patterns
- toast patterns
- error messaging
- date/time formatting


==================================================
N. UAT TASK TEST
==================================================

Pretend you are a real Member and complete these tasks:

TASK 1
    "Saya mau booking riding besok."

TASK 2
    "Saya mau tahu booking saya sudah dikonfirmasi atau belum."

TASK 3
    "Saya ternyata tidak bisa datang dan mau pindah jadwal."

TASK 4
    "Saya mau membatalkan booking."

TASK 5
    "Saya mau tahu apakah credit saya berkurang."

TASK 6
    "Saya mau lihat apakah ada perubahan dari BBS."

For each task record:

- Can user discover the action?
- Is the next step obvious?
- Is the outcome understandable?
- Is the feedback sufficient?
- Any confusion?
- Any dead end?
- Any incorrect state?
- Any technical error exposed?


==================================================
O. NO CODE CHANGES YET
==================================================

During this first audit:

DO NOT modify production code.

Create an audit report containing:

1. UX issues
2. Integration issues
3. Domain/UX mismatches
4. Missing states
5. Confusing terminology
6. Loading/error/empty state problems
7. Mobile/PWA issues
8. Authorization issues

Classify each issue:

    P0 — blocks core task
    P1 — serious usability/integration problem
    P2 — noticeable but workaround exists
    P3 — polish/improvement

Do NOT use overall UX scores or rankings.
